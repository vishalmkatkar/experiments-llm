The problem: real vendor documents are messy

When vendors send in documents, extraction gets hard because of three problems that show up together.

  1. Every vendor uses its own layout. One invoice puts the invoice number top right, another puts it in a footer, and a third labels it "Bill Ref". Line-item tables have different columns, column orders and wrapping rules.
  2. One file can contain several documents. Accounts-payable inboxes often get one scanned PDF holding three invoices, a credit note and a delivery slip.
  3. Documents can be long. A utility or logistics invoice can run to 30 or 40 pages, almost all of it line items.

A typical input looks like this: one 40-page PDF holding three invoices from two vendors. Two invoices are 2 pages each. The third is 36 pages, with a line-item table that starts on page 5 and doesn't end until page 39. Nothing in the file marks where one invoice stops and the next begins.

This post describes a pipeline that handles all three problems. It uses a supervised registry of known document formats to split files, find sections and extract each section separately. It also covers where that idea breaks and how to fix each weak spot.

Why "just send the whole PDF to an LLM" falls short

Current models can read very long PDFs, so the context window is no longer a hard wall. The real reasons to break documents up are accuracy, cost and control.

  • Accuracy drops on long inputs. Models skip or duplicate line items in long tables, mix up fields between documents in the same file, and get less reliable the further a value is from the start.
  • Cost grows with every page. Each retry or correction reprocesses the whole document.
  • Errors are hard to trace. If a total is wrong, you can't easily tell which page or region the bad value came from.
  • Output limits still apply. A 1,500-row line-item table may not fit in one response even when the input fits.

The fix is to give the model small, well-defined pieces of work: one document at a time, one section at a time, with a schema built for that section.

Core idea: a format registry

The whole system rests on a registry of known document formats, built and checked by people. Each entry describes one vendor's layout for one document type: what it looks like, how its pages are arranged, and where each section sits.

Part of the entryWhat it holdsUsed for
FingerprintVendor tax ID, distinctive keywords, logo hash, text embedding of page 1Recognising the format
Page rolesWhat a first page, continuation page and last page look likeSplitting files into documents
Section definitionsHeader, line items, totals, remarks, each with its boundariesCropping sections
Field hintsExpected labels such as "Invoice No" or "Bill Ref", and expected formatsGuiding extraction
Validation rulesWhich totals must add up, and which fields are requiredChecking the output

Define sections by anchors, not coordinates

The obvious way to mark a section is a fixed box, for example "line items are from y=320 to y=780 on page 1". That breaks as soon as a header gets longer, an address wraps onto an extra line, or a table has more rows than the sample did.

Define each section relative to text the page always contains:

{
  "section": "line_items",
  "start_anchor": { "text": "Description", "edge": "top" },
  "end_anchor": { "text": ["Subtotal", "Carried forward"], "edge": "top" },
  "continues_across_pages": true,
  "repeat_header_row": true
}

Anchors move with the content, so one template keeps working on a 1-page invoice and on a 36-page one.

Step 1: Classify pages and split the file

Before extracting anything, split the file into separate documents. In the research literature this is called page stream segmentation: you label each page, then group the pages.

Give each page one of these labels:

  • First page: has a header block, a new invoice number, or "Page 1 of N".
  • Continuation page: has the same invoice number, the line-item table carried over, or "Carried forward".
  • Last page: has a totals block, payment terms or a signature area.
  • Attachment: a delivery note, timesheet or cover letter that belongs with the document before it.

The registry makes this much more reliable. Once the fingerprint identifies the vendor, its page-role definitions say exactly what a first page looks like for that vendor. For unknown formats, a cheap page-level classifier (a small vision model, or text rules) fills the gap.

Start a new document wherever the invoice number changes, the vendor changes, or a page is labelled "first page". Check each group before moving on: a page count that doesn't match "Page X of N", or a document with no totals block, means the split needs review.

Step 2: Find and crop sections

For each document, use its template's anchors to find each section, then cut it into pieces the model can handle. The header is usually one piece. The line-item table is where most of the care goes.

Tables that run across pages

A 36-page table can't be one crop, and naive per-page crops cause three problems:

  • Rows split at page breaks. A description that wraps onto the next page ends up as half a row in each crop. Fix: overlap each chunk with the one before it by a row or two, then remove the duplicates when stitching.
  • Column headers missing. Page 17 shows numbers with no column names. Fix: crop the header row once from the first page and attach it to the top of every chunk.
  • Crops too large. One dense page can hold 60 rows. Fix: cap each chunk at a set number of rows, splitting at row boundaries found from table lines or whitespace.

Use the text layer when there is one

Screenshots aren't always the best input. Many vendor PDFs are generated digitally and contain an exact text layer with coordinates.

SourceWhat to send for each sectionWhy
Digital PDFText and coordinates within the anchor region, plus the crop image as backupExact characters, cheaper, no OCR errors
Scanned PDF or imageCrop image, plus OCR text if availableOnly option; the image keeps the layout
Mixed (stamps, handwriting)BothText for typed fields, image for annotations

Anchors also work best on the text layer: finding "Subtotal" in text is more reliable than finding it in pixels.

Step 3: Extract one section at a time

Each section type gets its own prompt and output schema. That's where most of the accuracy gain comes from: the model answers one narrow question at a time.

  • Header: a fixed set of fields (vendor, invoice number, dates, PO number, currency, tax IDs), using the field hints from the template.
  • Line items: an array of rows with fixed columns (description, quantity, unit price, tax, line total). Tell the model to return rows exactly as printed, without merging, summarising or calculating.
  • Totals: subtotal, tax lines and grand total.

Pass the document's context into every call

A crop of page 17 doesn't show the currency, the vendor or the PO number. Extract the header first, then include it in every line-item call:

Document context: Vendor = Acme Logistics, Currency = EUR, Invoice = INV-20931
Columns (from page 5): Date | Shipment Ref | Description | Qty | Rate | Amount
Chunk 7 of 22 (rows continue from previous chunk; first 2 rows overlap)
Return rows exactly as printed.

The extraction calls are independent of each other, so they can run in parallel. A 36-page invoice takes about as long as its slowest chunk, not the sum of all of them.

Step 4: Stitch and validate

Smaller inputs make extraction more accurate, but they don't prove the output is right. Confidence comes from checking the stitched result against the document itself.

Stitching. Join the chunks in order. Remove the overlapping rows by matching on row content and position, not on description alone, because real invoices repeat descriptions. Rejoin any row that was split at a page break.

Checks. An invoice contains its own answer key:

CheckRuleCatches
Line arithmeticquantity × unit price = line totalMisread digits, shifted columns
Table totalsum of line totals = subtotalMissed or duplicated rows
Grand totalsubtotal + tax − discounts = totalMissed tax lines or charges
Row countRows extracted match rows detected in the cropRows the model skipped
Cross-fieldDue date after invoice date; tax ID matches registry; PO exists in your ERPWrong field, wrong document

Routing. If every check passes, post the result automatically. If one fails, send only the affected section to a reviewer, showing its crop next to the extracted values. Because each value is tied to its crop, the reviewer checks one region instead of the whole 36-page document.

Handling vendors with no template

The biggest risk of a supervised registry is the labeling work. If every new vendor needs a person to mark up a template before its documents can be processed, the backlog grows faster than the team.

A general fallback path

When no fingerprint matches, the document goes through a path that needs no template:

  • A layout model (for example a table-detection or document-layout model) finds the header, table and totals regions.
  • If that isn't confident, a vision LLM is asked to return the section boundaries as anchors.
  • Steps 2 to 4 then run as normal: cropping, extraction, stitching and checks are the same either way.

Templates that build themselves

When a reviewer approves a result from the fallback path, the system already knows which anchors bounded each section and which labels matched each field. Save that as a draft template. After it passes on two or three more documents from the same vendor, promote it to active.

This turns the registry from something you build before going live into something that grows from normal use. People review results, which they would do anyway, instead of labeling templates.

Spotting layout changes

Vendors change their layouts without warning. Track the check failure rate for each template. If a template that usually passes 98% of the time drops sharply, mark it as stale. Its documents go to the fallback path, and the next approved result produces a new version of the template.

The whole pipeline

The registry speeds up known formats, but every document passes the same checks. Reviewed results from the general path feed new templates back into the registry.

What to watch in production

The template registry looks like the core of this system, but in practice the core is splitting, validation and review. Templates are an optimisation on top. These are the places where real deployments struggle.

  1. Splitting errors spread. If a file is split wrong, every later step works on the wrong unit. Scanned batches often lack "Page X of N", show the invoice number only on page 1, or include blank separator pages. Expect to spend more time on splitting than on extraction.
  2. Section crops can remove context. Current vision models handle a full page well, and a cropped header can lose nearby labels the model needs. Start with page-level chunks (one page, plus the column headers and the document context). Crop finer than a page only where you measure a gain.
  3. Anchors on scans need fuzzy matching. OCR turns "Subtotal" into "Subtota1" or "Sub total", and documents may be in other languages. Exact-match anchors fail without anyone noticing.
  4. Arithmetic checks need tolerances. Real invoices have rounding differences, tax per line versus tax on the total, several tax rates, freight, surcharges and discounts. Delivery notes have no totals at all, so their checks are weaker.
  5. Self-building templates need positions. To save a template, you need to know where each value was found on the page. LLMs report positions poorly. For digital PDFs, search the text layer for the extracted value; for scans, match it against OCR word boxes.
  6. Templates pay off only for high-volume vendors. Volume usually follows a Pareto pattern: roughly 20% of vendors produce 80% of documents. Build templates for that group and let the general path handle the rest.

A practical build order

  1. Build the baseline: split, chunk by page with document context, extract with a strong vision model, validate, review.
  2. Build a labelled test set of 200–500 real documents. Measure field-level accuracy and the straight-through rate (documents that need no human review).
  3. Add templates for high-volume vendors whose baseline error rate justifies them.
  4. Add section-level cropping only where page-level chunks measurably fail.

Trade-offs, and when not to use this

This pipeline has more parts than a single prompt. It's worth it when volume, document length or accuracy requirements are high, and overkill otherwise.

SituationRecommendation
A few vendors, short one- or two-page documents, low volumeWhole-document LLM extraction plus the Step 4 checks is enough
Many vendors, long documents, files with several documents in themThis pipeline
Very high vendor turnover, every document looks newLean on the fallback path; the registry adds little
Strict audit requirements (finance, tax)This pipeline: every value links back to its crop

Costs to plan for: running the registry and fingerprint matching, tuning anchors for awkward layouts, and the review interface. Most of this is built once and then shared by every vendor.

Conclusion: treat templates as a learned cache

Template-guided, section-by-section extraction solves all three original problems. The registry tells you what each document is and where it splits. Anchored sections let any page count go through fixed-size pieces of work. Checks against the document's own totals give you confidence you can measure.

Don't make templates a requirement. Make them a cache: use one when it exists, fall back to general layout detection when it doesn't, and let approved results build the next template. The system then improves with every document it processes, without a separate labeling project.
