# Template-guided, section-wise extraction with LangGraph

Reference code for the blog post
[Beyond the Context Window: Template-Guided, Section-Wise Extraction for Messy Vendor Documents](https://www.ingelenz.com/blog/beyond-the-context-window).

It processes one PDF that holds four invoices from three vendors, with nothing
marking where one ends and the next begins. It splits the file, extracts each
invoice section by section, and checks every result against the invoice's own
numbers. It runs locally with Ollama (`qwen2.5:7b`).

## Run

```bash
pip install -r requirements.txt     # from the repo root
ollama pull qwen2.5:7b

cd src
../.venv/bin/python -m app.template_extraction.main                       # every row through the LLM
../.venv/bin/python -m app.template_extraction.main --fast                # rules for clean rows, LLM for the rest
../.venv/bin/python -m app.template_extraction.main --drop-row INV-20958  # watch validation catch a missing row
../.venv/bin/python -m app.template_extraction.main --only INV-20958      # one document
../.venv/bin/python -m app.template_extraction.main --generate            # rebuild the sample PDF
../.venv/bin/python -m app.template_extraction.main --mermaid graphs/     # export both graphs
```

The sample PDF and its ground truth are in [`samples/`](samples/). They are
generated by [`sample_data.py`](sample_data.py) and built to include the hard cases:

| Invoice | Vendor | Pages | What it exercises |
|---|---|---|---|
| INV-20931 | Acme Logistics | 1–2 | Table across pages, "Carried forward" / "Brought forward" lines |
| BL-55120 | Brightline Office Supply | 3–4 | Different labels ("Bill Ref", "Net total") and page counter ("Sheet 1/2") |
| INV-20958 | Acme Logistics | 5–7 | 72 rows across 3 pages, a wrapped row split across a page break, two genuinely identical rows |
| CF-3381 | Cobalt Freight | 8 | A vendor with no template |

## How it maps to the blog

| Blog step | Code | LLM? |
|---|---|---|
| Format registry | [`registry/*.json`](registry/): fingerprint, page roles, page counter, anchor-based sections, field hints, validation rules | – |
| Use the text layer | [`pdf_text.py`](pdf_text.py): words grouped into lines, column gaps marked with ` \| ` | No |
| Step 1: classify and split | [`layout.py`](layout.py) `classify_page`, `split_documents` | No |
| Step 2: find sections | `locate_sections`: anchors, not coordinates; skips "Brought forward"; rejoins wrapped and page-split rows | No |
| Tables across pages | `make_chunks`: 15 rows per chunk, 2-row overlap, each row tagged with a position id | No |
| Step 3: extract one section at a time | [`extract.py`](extract.py): header first, then line-item chunks in parallel with the header passed in as context | Yes |
| Step 4: stitch | `stitch_node` in [`graph.py`](graph.py): de-duplicates overlap rows **by position id**, so identical-looking rows survive | No |
| Step 4: validate | [`validate.py`](validate.py): required fields, page counter, row count, line arithmetic, table total, grand total, overlap agreement | No |
| Vendors with no template | `generic_extract` → `validate` → `propose_template` writes a draft template to `out/candidates/` for human review | Yes |

There are two graphs:

```
File graph      load_pdf → classify_pages → split_documents → process_document (one Send per invoice)
Document graph  template?  locate_sections → extract_header → extract_chunk (one Send per chunk) → stitch → validate
                no template: generic_extract → validate → propose_template (only if every check passes)
```

## Results on the sample bundle

Measured on an Apple M1 with 16 GB, where `qwen2.5:7b` generated about 5 tokens per second.

| Mode | LLM calls | Time | Outcome |
|---|---|---|---|
| `--fast` | 4 (3 headers + 1 unknown vendor) | ~2.5 min | All 4 approved; 124/124 rows (every field, including dates and references) and 20/20 header fields match ground truth |
| `--fast --drop-row INV-20958` | 4 | ~2 min | INV-20958 flagged `needs_review`: row count 71 vs 72, table total off by the missing amount |
| default (every row through the LLM) | 14 (3 headers + 10 chunks + 1 unknown vendor) | ~32 min | All 4 approved; amounts, quantities, prices and descriptions correct on 124/124 rows; 20/20 header fields. That run also exposed the nullable-field problem below: the model left row dates and references empty. After the fix, a spot check returns them correctly; a full re-run is pending. |

At 5 tokens per second, output tokens dominate: the 72-row invoice needed six chunk
calls. On a faster machine or a hosted model the same run takes a few minutes.

## Things learned building it

- **Small models answer `null` when the schema allows it.** With `po_number: str | None`, `qwen2.5:7b` returned null for PO numbers printed clearly in the header, and with nullable `date` and `reference` it dropped them from every line item. All the checks still passed, because none of them use those fields. Making the fields plain strings ("empty string if absent") fixed both. Validation only protects what it checks.
- **Name the column order explicitly.** Given field names as "Columns", the model left `reference` empty on every Brightline row. Saying "after the row id, the cells are in this order: reference, description, ..." fixed it.
- **Position ids make stitching safe.** INV-20958 has two genuinely identical rows. De-duplicating overlap rows by content would merge them; tagging each detected row with an id (`r041`, `r042`) before extraction keeps both.
- **On a clean digital PDF, rules handle most rows.** When cells line up with the template's columns, parsing the text layer directly is exact and free. `--fast` sends only ragged rows to the LLM. Real-world files are messier, which is when the LLM path earns its cost.
- **Validation is what makes the output trustworthy.** The `--drop-row` run shows a single missing row failing two independent checks.

## Limits

- **Synthetic data.** Generated invoices are cleaner than real ones. The ground-truth scores show the pipeline works as designed, not how it performs on production documents.
- **Digital PDFs only.** Scanned files need OCR or a vision model (for example `qwen2.5vl`) for steps 1–3. The structure stays the same.
- **Rule-based layout.** Page roles and anchors are string matches. Production systems usually add a small page classifier for unknown formats.
